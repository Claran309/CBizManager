# Change Note: 后端认证基础设施

## 1. What Changed

本次新增了第一批可独立运行的 Go 后端基础能力，覆盖 OpenAPI 契约、账号与组织模型、数据库迁移、认证授权、平台建组、邀请码注册、健康检查、启动装配和 Docker 部署。

对外提供 10 个接口：登录、注册、刷新令牌、退出、当前用户、修改密码、平台建组、创建邀请码、存活检查和就绪检查。所有接口使用统一响应 Envelope 和稳定错误码，并通过 `X-Request-ID` 关联请求与日志。

这是一次后端功能、数据库结构、配置、测试和部署能力的组合变更。Flutter 客户端业务功能不在本批范围内。

## 2. Why This Change Was Needed

项目此前只有需求与客户端骨架，没有可供客户端联调的身份系统。若直接开始写页面，账号角色、首次改密、Refresh Token、组归属和邀请码等规则会被分散到各端，后续很难保证一致。

本次先把 OpenAPI 作为唯一接口契约，再让 Service、Repository 和 Handler 分层实现同一套规则。这样移动端和 Web 端之后只需遵守契约，不需要猜测后端字段或错误语义。

Redis 被设计为可选依赖：当前认证正确性完全依赖 MySQL 中的事实数据，Redis 故障只降低缓存能力，不阻止 API 启动。代价是本批不会使用 Redis 加速会话查询，但换来了更清晰的故障边界。

## 4. Core Flow After The Change

```text
HTTP request
  -> Request ID / Recovery / Access Log / CORS
  -> Bearer authentication and role guards
  -> Gin Handler: bind and validate DTO
  -> Domain Service: authentication and organization rules
  -> GORM Repository: transaction, row lock and audit
  -> Docker MySQL: source of truth
```

登录后的令牌流程如下：

```text
username + password
  -> bcrypt verification
  -> create hashed refresh session in MySQL
  -> issue short-lived access JWT + opaque refresh token
  -> refresh rotates session atomically
  -> old refresh token can no longer be replayed
```

## 5. Key Code Concepts

### 契约优先

OpenAPI 先固定路径、字段、状态码和错误码，Handler 再实现契约。客户端生成模型或手写请求时都可以把该文件作为事实来源。

### Refresh Token 轮换

Refresh Token 是随机的不可解释字符串，数据库只保存 SHA-256 哈希。刷新时旧会话与新会话在同一事务内完成撤销和创建，因此旧 Token 重放会返回 `AUTH_REFRESH_INVALID`。

### 状态即时失效

Access JWT 只证明令牌由服务签发。每个受保护请求仍会读取用户、组和 membership 状态，所以禁用用户、禁用组或移除成员后，不需要等待 JWT 自然过期才生效。

### 数据库约束与事务边界

“只能有一个平台管理员”“每组只有一个有效 owner”“邀请码只能消费一次”等规则不只写在 Go 判断中，也由唯一索引、事务和行锁保护。这样多个 API 实例并发时仍由 MySQL 给出最终一致结果。

### 可选 Redis

MySQL 决定 `/health/ready` 的 HTTP 状态；Redis 只报告 `up`、`down` 或 `disabled`。这表示 Redis 故障可以降低能力，但不能改变登录和权限判断的正确性。

## 6. Important Implementation Details

- 生产环境拒绝默认或过短的 JWT Secret，并要求显式配置 bootstrap 管理员用户名和至少 12 字节的临时密码。
- bootstrap 管理员使用唯一约束与 MySQL 1213 死锁重试实现幂等，多实例同时启动也不会创建多个管理员。
- 建组事务同时创建组、主账号、owner membership 和审计记录，任一步失败都会回滚。
- 邀请码明文只在创建响应中出现一次，数据库只保存哈希；消费时锁定邀请码记录并检查有效期、状态和组状态。
- 强制改密账号仍可登录，但只能访问本人信息、改密和退出接口，不能创建组或邀请码。
- Access Log 不记录 Authorization、Query 或请求体；Recovery 不输出 panic 值，只记录 Request ID 和堆栈。
- Docker 镜像使用多阶段构建和非 root `app` 用户。Compose 使用项目专用网络和命名卷，不复用现有 MySQL/Redis 数据卷。
- `.dockerignore` 明确排除 `.env` 和构建产物，避免秘密进入 Docker build context 或缓存层。

## 7. How To Verify

已执行以下基础验证：

```powershell
cd backend
gofmt -w .
go mod tidy
go mod verify
go test -count=1 ./...
go vet ./...
go build -o "$env:TEMP\cbizdocsmanager-api.exe" ./cmd/api
docker compose -f ..\deploy\docker-compose.yml config --quiet
docker build --tag cbizdocsmanager-api:local-test .
```

真实 Docker MySQL 验证使用从容器环境临时读取、未输出到日志的凭据执行：

```powershell
go test -count=1 -tags=integration ./... -v
```

真实 MySQL 测试覆盖迁移锁、dirty migration、单平台管理员约束、并发 bootstrap、完整认证闭环和邀请码并发消费。测试期间 Redis 保持停止，认证闭环仍通过。测试创建的临时数据库已自动删除，原 `MySQL` 容器也已恢复为停止状态。

`go test -race` 未作为本次通过门槛：当前 Windows GCC 报告 `cc1.exe: 64-bit mode not compiled in`，属于本机 C 工具链问题，不是 Go 测试失败。
