**A. 生产代码真 bug（SQLite 掩盖、真实 MySQL 必炸）**

1. `document` 模块 `Service.Create` / `Service.Update` **漏传 `Now`**（只有 `changeStatus` 传了）。
   仓储用它写 `audit_logs.created_at`、`idempotency_records.created_at`、`updated_at`；
   零值时间会被 MySQL 严格模式拒绝：
   `Error 1292: Incorrect datetime value '0000-00-00' for column 'created_at'`。
   SQLite 容忍零值日期，所以纯单测全绿、集成测试长期 SKIP，把这个漏洞藏到了现在。
   → 系统排查确认 settlement / reporting / organization / platform / finance 都正确传了 `Now`，

2. `platform` 模块 `ListGroups` 用 `Table("groups AS g")`。**`groups` 是 MySQL 8.0 保留字**
   （窗口函数的 `GROUPS` 帧单位），`Table()` 一旦带别名就走「原样 SQL」分支不做引号转义，
   真实 MySQL 直接 `Error 1064` 语法报错。SQLite 对保留字不敏感，单测照样过。
   → 修复：手写反引号 `Table("`groups` AS g")`。

   实测两种写法 SQL：
   - `Table("groups")` → ``FROM `groups` WHERE id = ? ORDER BY `groups`.`id` LIMIT ?`` ✅
   - `Table("`groups`")` → ``FROM `groups` WHERE id = ? ORDER BY `.`id` LIMIT ?`` ❌
   结论：不带别名交给 GORM；带别名且后续用 `Count`/`Scan`（不依赖 `Statement.Table`）才手写引号。

## 主题：Flutter 端 Task 3（会话级依赖 Scope 与销毁重建）

提交：`3630772 feat(client): 隔离认证会话级依赖`（8 files, +747/-89）。

### 一、做出来的东西

`client/lib/app/session_scope.dart`（新增）把 Provider 分成两层：

- **应用级**（进程内共享，不随登录登出重建）：`dioProvider`（刻意不给默认值）、
  `appDatabaseProvider`（默认 `null`）、`nativeCacheEnabledProvider`（默认 `false`）。
- **会话级**（不设默认实现，误读即抛 `StateError`）：`activeSessionProvider`、
  `memberRepositoryProvider` / `dictionaryRepositoryProvider`（由作用域装配）。

`AuthenticatedSessionScope` 是 `ConsumerWidget`，返回
`ProviderScope(key: ValueKey(session.scopeKey), overrides: ...)`；
`app.dart` 只在 `auth.session != null` 时包这一层，登出不渲染即卸载销毁。
`buildSessionOverrides(Ref, AuthSession)` 与 Widget 层共用私有 `_sessionOverrides`
（依赖显式传入），避免判断逻辑抄两遍。

### 二、最关键的一条：Riverpod 3 的传递式作用域必须显式声明 `dependencies`

第一版 5 个用例挂了 4 个，根因不是 Widget 层级，而是 **Controller 没被挂进子容器**：

- Riverpod 3 的 `ProviderPointerManager._upsert` 会调
  `findDeepestTransitiveDependencyProviderContainer`，
  **声明了 `dependencies:`（即 `$allTransitiveDependencies` 非空）的 Provider，
  会被挂到「覆盖了它依赖项的那个最深容器」里**；否则退回根容器。
- `MemberController` 只在**方法里** `ref.read(memberRepositoryProvider)`，
  `build()` 里没 watch ⇒ Riverpod 无从推断 ⇒ Controller 挂在根容器被所有会话共享。
  表现：两个会话容器读到的 `memberControllerProvider.notifier` **是同一个实例**，
  换账号后上一个人的列表不会消失。
- 修法：`NotifierProvider(..., dependencies: [memberRepositoryProvider])`。
  字典 Controller 同理。**凡是"会话级 Repository 只通过 `ref.read` 在方法里取用"的
  Controller，都必须手写这行**，否则隔离形同虚设。

### 三、其余踩到的坑

1. `notifier.state` 在 dispose 后写入会抛错 ⇒ 两个 Controller 加 `_disposed` 标记
   （`ref.onDispose` 里置位），所有写入点先判 `_disposed`；
   排队执行的写操作还要**在调用时就把 Repository 取好**——dispose 之后再碰 `ref` 也会抛。
2. Riverpod 3 中 provider 内部抛的异常会被包一层 `ProviderException`
   （`.exception` 里才是原始错误）再交给 `read` 调用方。测试断言要用
   `throwsA(isA<ProviderException>().having(...))`，不能直接 `throwsStateError`。
   （`overrides` 装配阶段抛的错不经过 provider，仍是裸 `StateError`。）
3. `Override` 与 `ProviderException` **不在** `package:flutter_riverpod/flutter_riverpod.dart`
   的导出里，要 `import 'package:flutter_riverpod/misc.dart' show ...`。
4. 同一个容器里重复覆盖同一个 Provider 会被直接断言拦下：
   `Tried to override a provider twice within the same container`。
   测试里不要「铺开一组 overrides 再追加同键覆盖」，要整份重写。
5. `app.dart` 一旦在已登录态包会话作用域，**任何**渲染真实应用的 Widget 测试都必须
   像 `bootstrap` 一样提供 `dioProvider`，否则 `AuthenticatedSessionScope.build` 当场抛
   `Bad state: Dio has not been configured`。这其实是好事：它把"真实装配缺应用级依赖"
   变成一次即时的、可见的失败，而不是运行期某个请求才 500。

## 主题：Flutter 端 Task 4（多角色 GoRouter 守卫矩阵）

提交：`4e2f315 feat(client): 添加多角色路由守卫矩阵`（14 files, +808/-41）。

### 一、守卫判定顺序（顺序本身就是语义）

`authRedirect(AuthState, location)` 严格按下面顺序，前一条命中就不再往下走：

1. `restoring` → 只能停 `/splash`（还不知道是谁，任何业务入口都不渲染）。
2. 未登录（`session == null`）→ 只允许 `/login` / `/register`。
   **用 `session == null` 而不是 `phase == unauthenticated`**，顺带把 release 下断言失效时
   可能出现的「已登录却无会话」也兜住：当成未登录是唯一不会泄露他人数据的降级方向。
3. `must_change_password` → 只能停 `/change-password`。**优先级高于角色分域**：
   改密没完成时连自己的角色首页都不该进。
4. 平台管理员 → 只能进 `/platform/*`。
5. 租户用户 → 不能进 `/platform/*`。
6. owner 专属 → `/invitations`、`/members/:id/permissions`。判 `accountType == groupOwner`，
   **不是判权限码**（`hasPermission` 对 owner 恒真，判权限码会放行持码的普通成员）。
7. `member.manage` → 普通成员进入 `/members` 的前提（owner 由 `hasPermission` 隐式通过）。
8. 已登录不该停在 `/splash` / `/login` / `/register` / `/change-password`。

**无权地址统一回角色首页**（`roleHome` = 平台管理员 `/platform/groups`，其余 `/home`），
绝不回登录页——用户是合法登录态，踢回登录页会让人以为被登出；而且回到一个「该角色必然有权」
的地址才能根除循环。

### 二、路由表与一个顺序陷阱

12 条稳定路由：`/splash`、`/login`、`/register`、`/change-password`、

### 二、Riverpod 3 的 family 写法（与 Riverpod 2 不同，别再写 FamilyNotifier）

Riverpod 3.3.2 **没有** `FamilyNotifier`。family 的创建函数签名是
`NotifierT Function(ArgT arg)` —— 也就是说**参数从 notifier 的构造函数进来**：

```dart
final platformGroupDetailControllerProvider =
    NotifierProvider.family<
      PlatformGroupDetailController, PlatformGroupDetailState, int
    >(PlatformGroupDetailController.new, dependencies: [platformRepositoryProvider]);

final class PlatformGroupDetailController
    extends Notifier<PlatformGroupDetailState> {
  PlatformGroupDetailController(this.groupId);   // arg 由 family 注入
  final int groupId;                              // 构造后不再变化，可以是 final

  @override
  PlatformGroupDetailState build() { ... }        // build 依旧无参
}
```

判定依据：`riverpod-3.3.2/lib/src/core/family.dart` 里 `ClassFamily._createFn` 的类型是
`NotifierT Function(ArgT arg)`；`builder.dart` 的 `NotifierProviderFamilyBuilder.call`
同样是 `NotifierT Function(ArgT arg) create`。

用**非 autoDispose**：本项目会话级 Provider 都由认证作用域整体销毁，少一层自动销毁
就少一处「被 read 到却立刻销毁」的时序陷阱（autoDispose 的 family 在测试里
`container.read(x.notifier)` 会立即销毁，必须额外挂 listen 才稳）。

### 三、五个关键设计决定

1. **乱序加载靠 generation**：`load` 先 `++_loadGeneration` 拿到本轮号，回来时
   `_isCurrent(gen)` 才允许写 state；`onDispose` 里也 `++`，让在途结果作废。
   注意 `query` 是**请求发出之前**就写进 state 的，这样 load 在途时调 refresh
   会按新条件刷，而不是按上一次的条件。
2. **冲突后「先重读、再放回失败」的顺序不能反**：`load()` 内部会 `clearFailure`，
   所以必须先 `await load()` 再把 ConflictFailure 塞回去。刷新不等于成功 ——
   数据确实变了，只是没变成用户要的样子，失败提示必须留到下一次成功操作之前。
   若重读本身也失败（例如断网），`load` 会写一个更新的 failure，此时**保留它**
   （`if (state.failure == null)` 才放回冲突原因）—— 断网比版本冲突更紧迫。
3. **列表页与详情页对 409 的处理刻意不同**：列表页只保留 failure，交给
   FailurePresenter 的 `shouldRefresh` 驱动「刷新后重试」提示（自动刷新会冲掉用户的
   翻页位置）；详情页保留 failure **并**自动重读（version 与候选列表过期后必须重读才有意义）。
   另外列表页启停成功后要用服务端回的新摘要替换该行，让 version 跟着涨，
   否则用户紧接着再点同一行会白撞一次 409。
4. **防重复提交的要点是「判空 + 置位之间不夹 await」**：
   `if (state.isSubmitting) return null;` 紧接 `state = state.copyWith(isSubmitting: true);`
   两行都是同步的，所以连点两次时第二次会直接返回；一旦中间插了 await 就失效。
5. **详情页 `changeOwner` 不替调用方改 draft 里的 version**：交接是不可逆的敏感操作，
   对话框打开期间组被别处改过时，正确做法是让服务端 409、我们重读最新详情让用户重新确认，
   而不是拿旧界面的意图去盖新数据。为此测试用例覆盖了「重读又失败」的分支。

### 二、Flutter 侧踩到的坑（单测才写得出来，务必记住）

1. **`NavigationBar` 要求 `destinations.length >= 2`，只有一个导航项会直接崩**
   （框架断言）。平台管理员恰恰只有「组管理」一个功能，所以 `ResponsiveScaffold`

   这个退化分支单独写了测试守着，否则将来有人「顺手」删掉判断，要等点开平台页才暴露。
2. **`TextFormField` 的 `decoration.errorText` 会被 validator 的结果覆盖**。
   `_TextFormFieldState` 构造输入框时执行 `copyWith(errorText: _errorText.value)`，
   validator 返回 null 时就等于把我传的 errorText 抹成 null。所以
   **服务端返回的逐字段错误必须合进 validator**（`失败时 setState 存 fields` →
   `_formKey.currentState!.validate()` 重跑），不能挂在 `InputDecoration` 上。
   配套：每个字段 `onChanged` 时清掉自己的服务端错误，否则「组名已存在」会一直挂着。
3. **`RadioListTile` 的 `groupValue` / `onChanged` 在当前 Flutter 版本已废弃**，
   用了会产生 `deprecated_member_use` → `flutter analyze` 非零退出。单选列表改用
   `ListTile(selected:, leading: Icon(radio_button_checked/unchecked), onTap:)` 自绘，
   更短、更稳，也不受版本更替影响。（同理：`DropdownButtonFormField.value` 已改名
   `initialValue`；本页用的是 `DropdownButton`，它的 `value` 没有改名。）

### 二、最值钱的坑：dispose 里不能同步改 Riverpod 状态

页面卸载时清掉明文（`_controller.clearSecret()`）在测试里直接炸：

```
'package:flutter/src/widgets/framework.dart': Failed assertion: line 5340:
'_lifecycleState != _ElementLifecycle.defunct': is not true.
#15 InvitationController.clearSecret (invitation_controller.dart:247)
#16 _InvitationsPageState.dispose (invitations_page.dart:85)
#17 StatefulElement.unmount
```

**根因**：`State.dispose()` 期间本 Element 已经进入 defunct 状态，而 Riverpod
把新 state 推给订阅者时会调 `markNeedsBuild` → 撞上「不要重建已销毁的 Element」的断言。
这不是测试环境特有的，线上同样会抛。

**解法**：`scheduleMicrotask(_controller.clearSecret);` —— 推到下一个微任务，
等这一轮卸载流程走完、订阅已摘掉再清，那时写 state 只落在状态里，不触发任何 build。
（`dart:async` 的 `scheduleMicrotask`。）

（provider 生命周期跟会话作用域走，不跟页面走），页面侧必须显式清，且**必须异步清**。

### 二、缓存语义：只有「不带筛选」才是权威全量

  - 写：筛选结果只是全量的子集，覆盖写会让下一次「全部成员」从缓存里读出残缺名单，
    而缓存是断网时唯一的兜底，它一旦残缺就再没有东西能纠正；
  - 回退：把全量缓存当作「关键词 alice 的搜索结果」返回，用户会看到一堆不匹配的人

成员缓存表只存展示字段，**没有账号 ID**，所以 `_readCachedMembers` 里写死 `userId: 0`。
这是刻意的：契约里 `UserSummary.id` 是 `minimum: 1`，0 不可能与真实用户撞上；
界面判断「这一行是不是我自己」时对缓存数据一律判不出来，
**宁可少禁用一次按钮（服务端还会再拒一次），也不能靠猜把某一行标成「你自己」**。
测试里专门有一个 `cachedMemberFromCache` 夹具钉住这件事。

### 四、Controller 的两条新规则

- `loadPermissionCatalog()` **已经拿到就不重复拉**（目录是后端固化的常量表）；
  失败时目录仍为空，所以重试路径天然可用 —— 这条要测（否则用户永远看不到复选框）。
- `loadPermissions(id)` **先清旧快照再发请求**：用户点开 B 的权限页时屏幕上若还留着 A 的
  勾选状态，他会拿一个错的基线去改，保存下去就是把 B 的权限替换成 A 那一套。
- 409 后的顺序仍然是「先重读、再把冲突原因放回去」（`load`/`loadPermissions` 都会
  `clearFailure`）；`replacePermissions` 的冲突要**连快照一起重读**，
  但只在「权限页确实开着这个成员」时才读（否则会凭空拉一份界面没在看的快照）。
- 重读本身也失败（断网）时保留那个更新的失败：「连不上」比「版本过期」更紧迫。

### 五、一个纯 Dart 测试坑（不是 Flutter 特有的）

给假仓储「注入一次失败」时**不要往队列里塞 `Future.error(...)`**：
它在测试体里被创建的那一刻还没有任何监听者，Dart 会把它当成**未处理的异步错误**
报给测试框架，用例就红在一个跟被测逻辑无关的地方（本次 `重读本身也失败` 就是这么红的）。
正确做法是给假仓储加一个**一次性错误标志**，在方法被调用时才构造失败的 Future ——
那时调用方紧接着 `await`，不存在裸露窗口。

  共享的 `MemberRowActions` 让卡片与表格**用同一套规则**决定按钮给不给 ——
  各写一遍，用户切到宽屏就会看到不一样的入口。

### 三、权限替换页：本地草稿的三条硬规则

1. **草稿不写回 state**。`_draft` 是「还没提交的意图」，不是服务端事实。写回
   `MemberState.permissions` 会让列表页也看到一份没保存的权限，而且「用户改主意了」无处安放。
2. **草稿按 `version` 播种**（`_draftVersion`）。版本一变（保存成功 / 冲突后重读 / 换了目标）
   就重新播种：把上一版的勾选当作这一版的起点，用户就会拿着过期基线去**整体替换**。
   实现是 `ref.listen` 里判断 `_draftVersion == incoming.version`，不等才 `setState` 重播。
3. **提交的是完整集合，不是差量**；版本号取自**快照**（`state.permissions.version`），
   不是页面状态。整体替换没有 version 就没有乐观锁。
4. 保存成功后 Controller 会把返回的新快照作为本地基线（列表行 + `permissions` 一起换版本），
   于是「没有改动」成立、保存按钮自动变灰 —— 不给用户白撞 409 的机会。

### 四、测试抓出来的一个真实设计问题（值得单独记）

「目录加载失败」用例最初红了：断言 `find.byType(CheckboxListTile) == findsNothing`，
实际有 1 个。根因是 `extraCodes`（成员身上有、目录里没有的权限码）在**目录为空**时会把
每一个权限码都算成「目录之外」，于是页面同时弹出「权限目录加载失败」卡片**和**一段
「这些码不在目录里，取消勾选即可收回」的误导说明 —— 真实原因只是这次没拉到目录。

→ 修法：`showExtras = catalog.isNotEmpty && extraCodes.isNotEmpty`。
**只有拿到目录之后才谈得上「目录之外的权限」**。这条不是测试写法问题，是实现缺陷。

### 五、`extraCodes` 为什么必须存在（反向的静默丢数据）

权限目录由服务端下发、客户端不维护自己的一份；但因此**也不能**把目录里没有的码从草稿里
抹掉：真出现这种码（后端新加的 / 已下线的 / 目录接口只返回子集），静默丢弃等于让管理员
在毫不知情的情况下收回了一项权限。所以照旧显示、可取消勾选，提交时原样带上。

### 六、失败提示要有「不重复说一遍」的判据

权限页同时有三个失败出口，不能同一条错误说两遍：
- 没有快照 → 整页交给 `AsyncStateView`；
- 目录为空 → 正文里那张「权限目录加载失败」卡片（自带重试按钮）；
- 其余（已有快照且目录非空）→ 才飘 SnackBar（冲突时带「重新加载」动作）。
实现：`shownInline = !hasSnapshotNow || next.permissionCatalog.isEmpty`，
`ref.listen` 里 `failure != null && !identical(failure, previous?.failure) && !shownInline` 才提示。
**冲突绝不自动重提**：`_reloadAfterConflict` 只重读 + 保留冲突原因，用户看着新基线重新决定。

### 七、路由层

`parseMembershipId` 与 `parseGroupId` 共用 `_parsePositiveId`（正整数、下界 1，契约 minimum:1），
但保留两个具名函数 —— 调用点读出来就是「成员编号」「组编号」，读错语义时没人拦得住你。
非法编号走 `redirect` 返回 `/members?notice=invalid_membership_id`（**不能在 builder 里 go()**，

### 三、`_merge` 原来只做了单向（真 bug）

### 四、假仓储在撒谎（第二类真问题）

同一轮 3 个用例红，另两个（`status 为 null 时停用后摘掉`、`显式筛已停用时启用后摘掉`）的根因是
**`FakeDictionaryRepository.changeStatus` 原样返回了 `entries.first`（旧状态）**。
真实服务端的 `changeStatus` 返回的是**变更后**的实体（status 已改、version +1），
控制器正是靠它把新状态合回列表 —— 假实现返回旧的，等于让断言测一个**假前提**，
而且会把排查方向带偏（看起来像合并逻辑错了）。

→ 重写假仓储的写方法：默认**按入参合成实体**（`changeStatus` 造 status 改后、version+1 的副本；
`update` 应用 draft 但不改 status；`create` 用 `maxId+1` 造新条目），
只在刻意要固定数据时才用 `writeResult` 覆盖；找不到 id 直接 `throw`（用例自己写错要立刻红在看得懂的地方）。
三个写方法改成 `async` 并用 `throw`，语义与「返回失败的 Future」一致且没有同步抛的时序差异。

### 五、editor 为什么「自带写操作」（有意偏离既有约定）

既有约定是「对话框只收意图，页面拿 draft 才调 Controller」（`ChangeOwnerDialog` 就是这么做的），
但那是**确认型**对话框。这里的输入是用户一个字一个字敲出来的：失败丢回页面 + 对话框立刻关闭，
等于他敲的一屏资料因为一次网络抖动就全没了。

所以 editor 自己调 Controller，并规定：
- **校验失败 / 网络失败**：内联横幅展示 + **保持打开**（用户敲的内容一个字都不丢）；
- **成功**：关掉（Controller 已把新数据合进列表）；
- **乐观锁冲突**：关掉并交回 `DictionaryEditorConflict(failure)`，由页面提示「刷新后重新操作」——
  手里那个 version 已作废，重试必然再失败，让用户对着一个必然失败的保存按钮反复点比什么都糟。

三个出口用 sealed `DictionaryEditorResult` 表达（`Saved` / `Conflict` / null=取消），
而不是「返回 draft 或失败」这种多态可空值 —— 混在一起这三条路迟早被写成两个 if。

配套两个细节：
- **页面在 editor 开着时抑制自己的 SnackBar**（`_editorOpen`）：错误已由对话框内联呈现，
  页面再飘一条就是同一条错误说两遍，而且提示条会被对话框挡住。冲突那条是在 `_openEditor`
  的 `switch` 里**主动**呈现的，不经过 listener，所以不会丢。
- 判断「本次写失败」不用另开返回值：`_write` 开工时会 `clearFailure`，
  所以 `await` 之后读到的非空 `state.failure` 一定是本次造成的。
- `PopScope(canPop: !isWriting)`：写操作在途时不让返回键/点外部关掉对话框，否则结果被丢掉，
  用户既看不到「保存成功」也不知道到底存没存上。

### 四、`AuthController.login` 的状态机（一处真缺陷）

原来 `login` 成功才写状态、失败直接抛异常、且**不设 `isSubmitting`**。改成与
`changePassword` 同构（开工置提交标记、失败写 failure 且吞掉异常）时踩到一个坑：

**失败后不能保留原 phase。** 初始状态是 `AuthState(restoring)`；
若失败时保留 `restoring`，守卫只允许 `restoring` 停在 `/splash`，
用户会被**永久留在启动页**上出不来。所以 `login` 失败一律落
`AuthPhase.unauthenticated`（登录的语义就是「试图建立会话」，没建立起来就一定是未登录）。
`changePassword` 则相反 —— 它必须保留已有会话，不能把人踢下线。
（这个坑是被 `auth_controller_test` 里「登录失败 ⇒ unauthenticated」的断言抓出来的。）

  + `validateRequired` / `validateMinLength`（**服务端错误优先于本地规则**）
  + `clearServerError(field)`（用户一改就清）。

### 一、FakeBackend 的设计（`test/support/fake_backend.dart`）

- **用 `HttpClientAdapter` 而不是 mock 单个 Repository**：实现一个内存状态机，
  塞进真实 `Dio`，于是 UI → Dio 拦截器 → `DioXxxRemoteDataSource` →
  FakeBackend → `fromJson` 严格解析，整条链路与生产一致。这才是「纵向闭环」——
  能验证「跨模块状态真的流动」（组交接后旧 owner 令牌失效、身份降级）。
- 内存状态机持有一切：platform admins / owners / members / groups / invitations /
  membersByGroup / dictionaries / 三类 token 表（accessToken→username、
  refreshToken→username）。错误码→HTTP 状态逐条对齐 `backend/pkg/apperror`
  （401=凭据类、403=FORBIDDEN/停用账号、404=NOT_FOUND、409=冲突、400=校验）。
- **安全铁律**（Task 计划 Step1 明确要求）：`toString()` 只打印各类资源数量；
  `failures` 列表只记 `method path -> code`，**不记请求体**（里面有密码/邀请码）。
  密码/令牌/邀请码明文在状态机内部持有，但绝不进任何诊断输出。
- 关键口径（对齐后端记忆里的不变量）：
  - **停用/降级的成员登录统一返回 `AUTH_INVALID_CREDENTIALS`**（防账号枚举），
    不是 403。这是旧 owner 交接后「登录被拒」的断言依据。
  - owner 交接：旧 owner 从 `_owners` 移除、降级为停用 member、令牌与刷新令牌
    全部清掉；新 owner（existing 或 new）写入 `_owners`。
  - 注册：邀请码 active 才可用，用掉后 status=used；**不签发令牌**（只回 user/group）。
- `/auth/me` 必须按 access token 反查身份并返回 `must_change_password` 快照 ——
  登录/改密后客户端都会用原令牌重读 me，缺这个端点整条链路断。
- 改密走 Authorization 头识别当前账号，**只对该账号**清改密标记（不能全清，
  否则会把别的账号也「免改密」了）。

1. **宽屏下邀请码/成员是表格，操作入口是文字按钮**（`查看`/`撤销`/`权限`），

### 二、money（`client/lib/core/money/money.dart`）

- 三个不可互换的不可变值类：`Amount`(分/scale2)、`UnitPrice`(万分之一元/scale4)、
  `Quantity`(千分之一/scale3)，内部 `BigInt` 存定点整数，**禁 double**。
- `parse` 严格校验：拒科学计数法、拒超精度非零尾数、去千分位逗号与 `+` 前缀、
  拒多小数点、拒空串。`format` 补零到 scale、`yuan` 去尾零。
- `add`/`sub`/`sum`、`isZero`/`isNegative`、`==`/`hashCode`。
- `Amount.mul(UnitPrice, Quantity)` 用 BigInt 四舍五入到分，对齐后端 `money.Mul`
  的「余数×2>=除数进位、负数向负（远离零）」规则，不溢出。

### 三、bizdate（`client/lib/core/bizdate/bizdate.dart`）

- `parseDate` 兼容 5 种写法（`2026-09-22`/`2026/9/22`/`2026 9 22`/`2026年9月22日`/
  `20260922`），折叠分隔符（含 `.`/`\`/`\t` 也折叠成 `-`），回读校验拒绝 `2026-02-31`，
  年份 `[2000,2100]`，返回 UTC 零点。
- `parseMonth` 只收 `YYYY-MM`（**月份不强制补零**，`2026-9` 合法，对齐后端），
  返回 `(当月起点, 次月起点)` 左闭右开。
- `formatMonth` → `YYYY-MM`；`formatMonthCompact` → `YYYYMM`（拼单号用）。
