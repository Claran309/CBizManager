**A. 生产代码真 bug（SQLite 掩盖、真实 MySQL 必炸）**

1. `document` 模块 `Service.Create` / `Service.Update` **漏传 `Now`**（只有 `changeStatus` 传了）。
   仓储用它写 `audit_logs.created_at`、`idempotency_records.created_at`、`updated_at`；
   零值时间会被 MySQL 严格模式拒绝：
   `Error 1292: Incorrect datetime value '0000-00-00' for column 'created_at'`。
   SQLite 容忍零值日期，所以纯单测全绿、集成测试长期 SKIP，把这个漏洞藏到了现在。
   → 系统排查确认 settlement / reporting / organization / platform / finance 都正确传了 `Now`，
   **只有 document 有**。修复：Create/Update 补 `Now: s.now().UTC()`。

2. `platform` 模块 `ListGroups` 用 `Table("groups AS g")`。**`groups` 是 MySQL 8.0 保留字**
   （窗口函数的 `GROUPS` 帧单位），`Table()` 一旦带别名就走「原样 SQL」分支不做引号转义，
   真实 MySQL 直接 `Error 1064` 语法报错。SQLite 对保留字不敏感，单测照样过。
   → 修复：手写反引号 `Table("`groups` AS g")`。
   **但反过来有陷阱**：`loadAccessState` 里的 `Table("groups")`（不带别名）配 `First()` 时
   **绝不能手写反引号**——那会让 `Statement.Table` 落空，GORM 拼出 `ORDER BY `.`id`` 的语法错误。
   实测两种写法 SQL：
   - `Table("groups")` → ``FROM `groups` WHERE id = ? ORDER BY `groups`.`id` LIMIT ?`` ✅
   - `Table("`groups`")` → ``FROM `groups` WHERE id = ? ORDER BY `.`id` LIMIT ?`` ❌
   结论：不带别名交给 GORM；带别名且后续用 `Count`/`Scan`（不依赖 `Statement.Table`）才手写引号。

## 主题：Flutter 端 Task 3（会话级依赖 Scope 与销毁重建）

提交：`3630772 feat(client): 隔离认证会话级依赖`（8 files, +747/-89）。

### 一、做出来的东西

`client/lib/app/session_scope.dart`（新增）把 Provider 分成两层：

- **应用级**（进程内共享，不随登录登出重建）：`dioProvider`（刻意不给默认值）、
  `appDatabaseProvider`（默认 `null`）、`nativeCacheEnabledProvider`（默认 `false`）。
- **会话级**（不设默认实现，误读即抛 `StateError`）：`activeSessionProvider`、
  `memberRepositoryProvider` / `dictionaryRepositoryProvider`（由作用域装配）。

`AuthenticatedSessionScope` 是 `ConsumerWidget`，返回
`ProviderScope(key: ValueKey(session.scopeKey), overrides: ...)`；
`app.dart` 只在 `auth.session != null` 时包这一层，登出不渲染即卸载销毁。
`buildSessionOverrides(Ref, AuthSession)` 与 Widget 层共用私有 `_sessionOverrides`
（依赖显式传入），避免判断逻辑抄两遍。

### 二、最关键的一条：Riverpod 3 的传递式作用域必须显式声明 `dependencies`

第一版 5 个用例挂了 4 个，根因不是 Widget 层级，而是 **Controller 没被挂进子容器**：

- Riverpod 3 的 `ProviderPointerManager._upsert` 会调
  `findDeepestTransitiveDependencyProviderContainer`，
  **声明了 `dependencies:`（即 `$allTransitiveDependencies` 非空）的 Provider，
  会被挂到「覆盖了它依赖项的那个最深容器」里**；否则退回根容器。
- `MemberController` 只在**方法里** `ref.read(memberRepositoryProvider)`，
  `build()` 里没 watch ⇒ Riverpod 无从推断 ⇒ Controller 挂在根容器被所有会话共享。
  表现：两个会话容器读到的 `memberControllerProvider.notifier` **是同一个实例**，
  换账号后上一个人的列表不会消失。
- 修法：`NotifierProvider(..., dependencies: [memberRepositoryProvider])`。
  字典 Controller 同理。**凡是"会话级 Repository 只通过 `ref.read` 在方法里取用"的
  Controller，都必须手写这行**，否则隔离形同虚设。

### 三、其余踩到的坑

1. `notifier.state` 在 dispose 后写入会抛错 ⇒ 两个 Controller 加 `_disposed` 标记
   （`ref.onDispose` 里置位），所有写入点先判 `_disposed`；
   排队执行的写操作还要**在调用时就把 Repository 取好**——dispose 之后再碰 `ref` 也会抛。
2. Riverpod 3 中 provider 内部抛的异常会被包一层 `ProviderException`
   （`.exception` 里才是原始错误）再交给 `read` 调用方。测试断言要用
   `throwsA(isA<ProviderException>().having(...))`，不能直接 `throwsStateError`。
   （`overrides` 装配阶段抛的错不经过 provider，仍是裸 `StateError`。）
3. `Override` 与 `ProviderException` **不在** `package:flutter_riverpod/flutter_riverpod.dart`
   的导出里，要 `import 'package:flutter_riverpod/misc.dart' show ...`。
4. 同一个容器里重复覆盖同一个 Provider 会被直接断言拦下：
   `Tried to override a provider twice within the same container`。
   测试里不要「铺开一组 overrides 再追加同键覆盖」，要整份重写。
5. `app.dart` 一旦在已登录态包会话作用域，**任何**渲染真实应用的 Widget 测试都必须
   像 `bootstrap` 一样提供 `dioProvider`，否则 `AuthenticatedSessionScope.build` 当场抛
   `Bad state: Dio has not been configured`。这其实是好事：它把"真实装配缺应用级依赖"
   变成一次即时的、可见的失败，而不是运行期某个请求才 500。

## 主题：Flutter 端 Task 4（多角色 GoRouter 守卫矩阵）

提交：`4e2f315 feat(client): 添加多角色路由守卫矩阵`（14 files, +808/-41）。

### 一、守卫判定顺序（顺序本身就是语义）

`authRedirect(AuthState, location)` 严格按下面顺序，前一条命中就不再往下走：

1. `restoring` → 只能停 `/splash`（还不知道是谁，任何业务入口都不渲染）。
2. 未登录（`session == null`）→ 只允许 `/login` / `/register`。
   **用 `session == null` 而不是 `phase == unauthenticated`**，顺带把 release 下断言失效时
   可能出现的「已登录却无会话」也兜住：当成未登录是唯一不会泄露他人数据的降级方向。
3. `must_change_password` → 只能停 `/change-password`。**优先级高于角色分域**：
   改密没完成时连自己的角色首页都不该进。
4. 平台管理员 → 只能进 `/platform/*`。
5. 租户用户 → 不能进 `/platform/*`。
6. owner 专属 → `/invitations`、`/members/:id/permissions`。判 `accountType == groupOwner`，
   **不是判权限码**（`hasPermission` 对 owner 恒真，判权限码会放行持码的普通成员）。
7. `member.manage` → 普通成员进入 `/members` 的前提（owner 由 `hasPermission` 隐式通过）。
8. 已登录不该停在 `/splash` / `/login` / `/register` / `/change-password`。

**无权地址统一回角色首页**（`roleHome` = 平台管理员 `/platform/groups`，其余 `/home`），
绝不回登录页——用户是合法登录态，踢回登录页会让人以为被登出；而且回到一个「该角色必然有权」
的地址才能根除循环。

### 二、路由表与一个顺序陷阱

12 条稳定路由：`/splash`、`/login`、`/register`、`/change-password`、

### 一、`core/presentation/` 三个组件

**ResponsiveScaffold**（`responsive_scaffold.dart`）
- 断点 `kResponsiveScaffoldBreakpoint = 720` 逻辑像素。
- 窄屏：`Scaffold + AppBar + NavigationBar`；宽屏：`Scaffold + AppBar + Row(NavigationRail | VerticalDivider | Expanded(body))`。
- `AppDestination{label, icon, route}` 只描述「叫什么 / 长什么样 / 去哪」，两种布局共用一份。
- **高亮解析**：先精确匹配，再取**最长**路径前缀 —— 这样 `/members/7/permissions` 点亮
  「成员」、`/platform/groups/new` 点亮「组管理」；取最长是为了多个前缀都能命中时选更具体的。
- **点当前项直接 return，不 `context.go`**：否则会重建页面，丢掉滚动位置与未提交表单。
- 无障碍：导航项带 `label` + `tooltip`；`build` 里 assert「AppBar 的 IconButton 必须有 tooltip」。

**AsyncStateView**（`async_state_view.dart`）
- 判定顺序 **失败 > 加载 > 空 > 内容**。失败优先 = 不把原因藏在转圈后面；
  加载优先于空态 = 避免首次加载先闪一下「暂无数据」。
- 「刷新时保留旧列表」：调用方传 `isLoading: state.isLoading && state.items.isEmpty`。
- `loadingMessage` / `emptyMessage` 必须可覆盖（不同页面语义差别大）。

**FailurePresenter**（`failure_presenter.dart`）
- 输出 `FailurePresentation{message, fieldErrors, requestId, shouldLeavePage, shouldRefresh}`。
- `ValidationFailure` → 原样保留服务端 message + fields；
  `ConflictFailure` → **丢弃**服务端底层文案（如 version 号）换成
  「数据已被其他操作修改，请刷新后重新操作」+ `shouldRefresh=true`；
  `ForbiddenFailure` → `shouldLeavePage=true`；
  `UnauthenticatedFailure` → **两个标记都不设**（会话失效由全局单飞刷新 + 守卫统一处理，
  页面再跳一次会与守卫抢跑）；`NetworkFailure` → 文案必须点明「需要联网」；
  `ServerFailure` → 服务端 message + requestId。
- 失败视图里 Request ID 用 `SelectableText`（唯一用途就是被复制走），
  冲突时按钮文案变「重新加载」，其余为「重试」（同一个 `onRetry` 回调）。

### 二、两个被框架/规格逼出来的决定

1. **`NavigationBar.selectedIndex` 是非空 `int` 且 `assert(0 <= i < destinations.length)`**，
   而 `NavigationRail.selectedIndex` 是 `int?`（允许"无选中"）。所以内部解析出的索引是
   `int?`：Rail 直接传（无匹配时 null 更准确），Bar 传 `?? 0` 兜住断言。
   另外 `NavigationBar` 还要求 `destinations.length >= 2`。
2. **`AsyncStateView` 实现为无类型参数**：计划写作 `AsyncStateView<T>`，但 `T` 不出现于
   该 API 的任何位置（全是布尔 / 回调 / `Widget`），留着只会逼每个调用点写一个不携带信息的
   类型实参。已在代码注释与提交信息里写明这是有意偏离。

### 二、几个值得记住的决定

1. **`changeOwner` 写完立刻重读详情**。契约里 `changeGroupOwner` 的响应是
   `OwnerChangedData{group, owner}` —— **没有** `member_counts` / `owner_candidates`。
   但计划里该方法的返回类型是 `PlatformGroupDetail`。唯一能满足签名的做法就是
   PUT 成功后再 GET 一次详情，好处是调用方拿到的数据自洽（被提升者已从候选人里消失）。
   测试里显式断言了 `['PUT','GET']` 两次请求；写用例时注意假适配器要**按 method 分发**，
   否则重读那步会拿到写响应而解析失败（第一版就是这么红的）。
2. **两种交接模式的请求体靠 sealed + switch 穷尽匹配生成**，不是「大对象 + 可空字段」。
   新增模式会直接编译报错。测试断言另一种模式的字段**一个都不能出现**。
3. **平台仓储不接本地缓存与 Outbox**。平台管理员没有 group，缓存键只能落到
   `group_id=0`；而停用整组 / 交接主账号是全局破坏性操作，离线排队偷偷执行更危险。
   有测试守着：跑完五个方法后 `listOutboxOperations/listCachedMembers/
   listCachedDictionaryEntries` 必须全空。
4. **`GroupMemberCounts` 三个键必填、且非负**。契约把它描述成松散 map（只约束值是整数），
   但缺键时退化成 0 会显示「活跃成员 0 人」这种会让人以为组被清空的假数字。
   Go 侧 `map[string]int` 零值键不会消失，所以严格假设成立。
5. **`PlatformOwner` 刻意不解析 `account_type`**：在「组主账号」「候选人」这两个位置上
   它恒定，解析进来只是冗余状态。

### 三、两个 dart 语法坑（analyze 直接抓出来的）

- **命名构造函数不能带类型参数**：`factory PageResult<T>.fromJson(...)` 是错的，
  必须写 `factory PageResult.fromJson(...)`；调用处照旧写 `PageResult<int>.fromJson(...)`。
  报错信息会散成 6 条（duplicate_constructor / type_parameter_on_constructor / ...），
  看着像语法炸了，其实就这一处。
- **sealed 基类用位置参数、子类用 `required super.version` 不匹配**。
  基类要写成 `const OwnerChangeDraft({required this.version});`（命名参数），
  子类才能 `required super.version`。
