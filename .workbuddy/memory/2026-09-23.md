### 数据模型与设计取舍（新模块必须沿用的新不变量）

- **总结算快照与结算单分成两张表**：`settlements` 是「按源单据申请 + 单级审批」的业务流程，会占用源单据（`active_document_id` 唯一键）；`report_snapshots` 是「按周期自动聚合」的只读报表，**没有审批流、不占用任何源单据**——同一张单据可以既出现在结算单里又出现在当月总结算里。把两者塞一张表会让「占用 / 释放」规则凭空长到报表头上。
- **汇总模块只有「看全组」一种数据范围，没有权限直接 403**（不是返回空结果）。需求把「汇总」定义为一项独立子账号权限；拿到它的人本来就该看全组。**返回空报表比明确拒绝更危险**——会让人以为「本月确实没有数据」。业务员看自己的月度数据走单据模块的 `/monthly-summary`，不受此影响。权限复用 `report.view`（看板与生成总结算共用一个码，避免「能看汇总却不能生成」的权限空洞）。
- **只统计 `status=submitted` 单据**：草稿金额未定、作废单已失效、跨月 / 跨组一律排除。
- **已付 / 已收 / 已开金额不按发生日期过滤**（取「截至当前的余额」口径）：需求要的是本周期单据的应付 / 应收余额，而不是「本周期发生了多少笔流水」。若按发生日期过滤，上月已付、本月付清的单一分钱都不会计入本月已付，未付款会被长期高估。
- **未结清单据数必须逐单比较，不能总额相减**：一张单多付、另一张单少付，总额相减会正好抵消，把「有 1 张单没付清」藏起来。因此 `LoadSettlements` 取回逐单的总额与三类记录合计，在 Go 里 `newPeriodTotals` 逐单聚合（而不是 SQL 的 `SUM(CASE WHEN ...)`）。
- **明细统计分两层，明细行不含已付 / 未付**：付款记录挂在单据上而不是某一行明细上，一张单里既有螺纹钢又有盘螺时，那笔付款算在哪个品名头上无从推导。硬摊到明细行只会得到「数字自洽、业务上经不起追问」的假精确报表。因此「合计块」是单据粒度的精确数字，「明细行」只给金额与数量。
- **毛利率用百万分之一整数（ppm）存储**：207500 = 20.75%，避免 IEEE-754 的 20.749999999999996 展示瑕疵。`ppmRatio` 用 `big.Int` 先乘 1e6 再除（钢材单价 × 数量容易接近 int64 上限），四舍五入到整数。占比展示文本由服务端统一给（`percentText`，两位小数如 "26.83"），三端不会各写一套除法产生显示差异。
- **明细分组必须带 unit**：`SUM(quantity)` 只有在单位一致时才有意义，把「吨」和「支」加在一起会得出看似有值、实际无意义的数字。分组键 = 往来单位 + 品名 + 型号 + 单位。
- **明细分页的 total 用「分组后的行数」而不是明细条数**：否则客户端以为还有好几页，翻过去全是空页。
- **快照即冻结，无 version 列、无修改接口**：生成时一次性写入入库 / 出库 / 毛利润 / 毛利率 / 三类销售金额；源单据事后修改或作废都不改变已生成数值。要更正只能重新生成一张，两张都留着便于追溯。
- **业务员姓名随快照落库**（不只存 user_id）：用户改名或注销后，历史报表仍要能说明「当时这一行是谁的」。回读时优先用冻结的那份姓名。
- **单号 `ZJS + YYYYMM + -4位当月序号`**（如 `ZJS202609-0003`），与结算单同构；**批次号取本批第一张快照的单号**（一次生成动作的多行共用），既不用额外生成规则，又能一眼看出「这次生成了哪几张」。序号仍走「取当月最大序号 + 1、唯一索引撞车重试」，不用悲观锁。
- **审计逐张写**（不是整批一条）：审计查询要能按单号定位到「这张总结算单是谁生成的」，整批只写一条会让业务员维度的多张单只剩一个笼统批次记录。
- **三类销售金额按固定顺序 Y-1 / y-N / N 返回**，缺哪类补 0：顺序随金额浮动会让使用者在不同月份看到结构不同的报表。
- 非负收敛：`Unpaid()` / `Uninvoiced()` / `Unreceived()` 把负值收敛为 0。理论上不会为负（财务模块在事务内锁单据行校验上限），但历史数据 / 并发修复 / 人工改库都可能留下超额记录，汇总层宁可显示 0 也不要显示「未付款 −1000 元」。
