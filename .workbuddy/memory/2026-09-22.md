## Task 6 结算与审批后端模块（已完成）

新增 `backend/internal/settlement/`（model / dto / normalize / service / repository / handler 七件套 + service_test / repository_test / handler_test，共 30 个用例），迁移 `000005_settlements.{up,down}.sql`。

数据模型与设计取舍：
- `settlements`：主表，落库三项金额快照（进项合计 / 销售合计 / 毛利润）与审批结论；单号 `JS + YYYYMM + -4位当月序号`（如 `JS202609-0003`），唯一键 `(group_id, settlement_no)`。
- `settlement_sources`：永久保留结算单 ↔ 源单据关联（含单号 / 业务员 / 日期 / 金额快照），满足「结算单可追溯到所有源单」。
- `approval_records`：申请 / 通过 / 驳回逐条追加，只增不改。
- **金额快照而非实时重算**：源单据后续改单或作废都不影响已生成结算单的数值。
- **「同一源单据不允许被两张有效结算单同时引用」用唯一索引兜底**：`active_document_id` 是 `document_id` 的活跃副本（占用时=document_id，驳回释放后置 NULL），唯一键 `(group_id, active_document_id)`；MySQL/SQLite 唯一索引允许多个 NULL，因此同一源单据可出现在多张历史驳回单里，但同一时刻只能被一张有效结算单引用。仓储另做加锁预检（`ensureSourcesFree`）优先给友好错误。
- 单级审批：通过与驳回都是终态，重复审批返回 `SETTLEMENT_STATUS_INVALID`；驳回必须填原因（`SETTLEMENT_REMARK_REQUIRED`）并释放源单据，业务员改单后可重新申请。
- 幂等复用 `idempotency_records`，`scope = settlement.create`，带 sha256 载荷指纹；单号撞车用唯一索引重试（`maxSettlementNoAttempts=5`）。
- 权限：审批资格由 `settlement.approve` 收敛（主账号默认拥有）；可见范围复用 `document.view_others`（子账号默认只看本人，未授权返回 false 而非 403）。

本轮被测试暴露并修掉的三处口径问题（重要）：
1. `pkg/bizdate` 新增 `FormatMonthCompact`（YYYYMM）。原先单号用 `FormatMonth` 会生成 `JS2026-09-0001`，与原型约定的 `JS202609-0003` 不一致，且与 LIKE 前缀口径也错位。
2. 仓储创建结算单时**显式用注入时钟写 `created_at` / `updated_at`**，不再让 GORM 取墙上时间。单号月份来自入参时钟、列表又按 `created_at` 过滤月份，两者取不同时间会在跨月瞬间出现「单号 10 月、列表归 9 月」的错位。

### 环境坑（下次别再踩）
- 本会话的 bash shim 里 **`head` / `tail` / `grep` / `find` 都不可用**（`dirname: command not found` 之类的 shim 报错），`docker` 也不可解析。**不要用管道 `| head` / `| tail` 来看输出**，否则会把真实输出吞掉、误判成「命令没输出」。要过滤输出请写 python 脚本或直接用对应工具。

## Task 7 付款 / 收款 / 开票后端模块（已完成）

新增 `backend/internal/finance/`（model / dto / normalize / service / repository / handler 七件套 + service_test / repository_test / handler_test，约 48 个用例），迁移 `000006_finance_records.{up,down}.sql`。

数据模型与设计取舍：
- **三类记录共用一张 `finance_records` 表 + `kind` 判别列**（payment 挂入库单 / receipt 挂出库单 / invoice 挂入库单），与 documents、settlements 同构；组隔离、幂等、审计、数据范围这些横向能力只写一遍。
- 表列：`group_id` / `document_id` / `document_kind`（kind 枚举副本，便于结清视图直接按方向过滤）/ `document_no` / `party_name` / `business_user_id` / `business_date` / `kind`（payment/receipt/invoice）/ `amount` / `occurred_on` / `method`（transfer/private_card/public_account）/ `method_note` / `card_tail CHAR(4)` / `invoice_no` / `remark`；索引按单据、按月、按业务员。
- **结清视图一律服务端推导，不落冗余状态列**：`Statement` 聚合提供 `SumByKind` / `CountByKind` / `Outstanding`，Dup 出「已付 / 未付 / 已收 / 未收 / 已开票 / 开票状态」。
- **记录类型由路由注入 Handler，请求体一律不接受 `kind`**（`CreateFinanceRecordRequest` 刻意不声明该字段），防止客户端伪造类型把记录挂到错误单据。
- **累计金额上限在事务内锁单据行校验**：`findDocumentLocked` 先 `SELECT ... FOR UPDATE` 锁单据行 → 复检状态/类型 → 幂等重放检查 → 锁内 `SUM` 校验是否超单据金额（超则 `ErrAmountExceeds`）→ 写记录 / 幂等 / 审计。
- **撤销 = 硬删除记录 + 同步清理指向该记录的幂等记录 + 审计**：删掉幂等记录后同一幂等键可重新登记（额度随之回收）。
- 对私卡只存卡号后 4 位（`card_tail`，脱敏），完整卡号不落库。
- 登记与撤销共用 `finance.record` 权限码（`internal/authorization` catalog 与 member 权限目录同步到 7 项）。
- 数据范围：主账号全权限；子账号默认只看本人，`finance.record` 控制登记/撤销，`document.view_others` 控制看他人；**结清视图 `statementData` 也做数据范围校验**（成员不能靠猜 document_id 读他人结清视图）。
